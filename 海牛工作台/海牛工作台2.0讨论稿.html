    02 当前问题

    传统研发模式面临的挑战

    ⚠️

    产品定位不清

    缺少统一的价值表达和产品定位，客户难以快速理解产品核心能力

    📦

    功能分散

    各功能模块独立散落，缺少统一入口和协同机制，用户体验割裂

    🌐

    能力孤岛

    需求、开发、测试各环节独立运作，未形成完整的交付链路闭环

    👥

    角色割裂

    产品、设计、开发、测试各角色缺少统一的工作流平台，协作成本高

    💎

    价值不显

    企业研发资产未被有效沉淀和展示，无法体现持续积累的价值

    🔄

    缺少闭环

    没有最小验证路径（MVP），难以快速验证产品方向和迭代优化

    🎨

    形态落后

    页面风格偏传统后台管理，缺少现代化AI工作台的视觉体验

    06 MVP

    一期聚焦产品经理应用与前端开发应用，通过交付包、版本管理、变更管理形成最小闭环。

    🔴 P0 必做：不做闭环跑不通 🟡 P1 轻量/占位：二期完善 ⚪ P2 架构预留：暂不开发

    产品经理应用｜可独立部署 / 独立售卖

    创建项目 上传需求资料 AI需求分析 待确认问题 功能清单 PRD生成 流程图/页面清单 MyBricks原型生成 开发说明 提交开发 交付包版本 需求变更提交 项目资产沉淀

    前端开发应用｜可独立部署 / 独立售卖

    接收交付包 查看原型 查看PRD 查看页面说明 查看开发说明 获取代码包 基于代码包二开 页面/组件开发 断点调试 前端联调 接收变更包 版本合并/回退 组件资产沉淀
    中间边界：交付包中心

    产品不直接查看或修改开发代码；产品输出原型、文档和初始代码包，前端基于交付包开发。新需求通过变更包同步，不覆盖开发成果。

    平台底座能力｜支撑两个独立应用解耦协作

    项目中心 交付包中心 MyBricks能力接入 版本管理 变更管理 角色权限边界 项目资产中心 后端应用接入 测试应用接入 第三方应用市场

    MVP最小闭环流程图

    产品经理应用

    1. 创建项目 / 上传需求资料
    2. AI需求分析 / 待确认问题
    3. 生成功能清单 / PRD / 页面清单
    4. MyBricks生成原型 + 初始代码
    5. 提交开发：生成交付包 V1
    6. 新需求：提交变更单 / 生成交付包 V2
    →
    交付包中心
    原型 + PRD + 页面说明 + 开发说明 + 代码包
    →
    版本 / 变更中心
    V1 / V2 对比、影响范围、合并确认

    前端开发应用

    1. 接收交付包 V1
    2. 查看原型 / PRD / 开发说明
    3. 获取代码包，创建开发分支
    4. 页面开发 / 组件开发 / 断点调试
    5. 接收变更包 V2，查看差异影响
    6. 合并变更 / 回退版本 / 提交开发成果
    核心原则：产品经理应用和前端开发应用可以独立售卖、独立部署；两者不直接耦合，通过交付包、版本管理、变更管理协作。产品不能直接修改开发代码，开发也不反向覆盖产品原型。
